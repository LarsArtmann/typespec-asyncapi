# Status: v1.2.0 npm publish gap + website refresh (2026-11-19)

**Session trigger:** "We published v1.2.0 but our website still seems out of date!"
**Scope:** this session only — diagnosis, website refresh, publish recovery attempt, live verification.

---

## The headline finding

v1.2.0 was **never actually published to npm**. The GitHub release exists
(2026-11-19 13:03 UTC), `package.json` and `CHANGELOG.md` say 1.2.0, but npm
still serves `latest = 1.1.0`. The chain of failures:

1. Tag-push run (44529186193) failed — `NPM_TOKEN` secret had expired and was deleted.
2. The recovery `workflow_dispatch` (44599637231) ran with the **default `dry_run=true`** —
   it "succeeded" while publishing nothing (publish + github-release jobs skipped).
3. This session dispatched the real publish (`dry_run=false`, run 44603780129).
   Verify job green (1333 tests, 96.9% avg coverage, 0 clones — numbers reused for
   the website status table). **Publish failed E404** on `PUT registry.npmjs.org`:
   the OIDC identity authenticated and even signed a provenance statement, but npm
   does not know this workflow — the **one-time trusted-publisher registration was
   never done** (a Lars action, 2FA, npmjs.com UI).

Meanwhile the website was stale on two independent axes: repo content still said
1.1.0, and the live site had not been deployed since **Oct 23** (deploys are
manual: `nix run .#deploy-website`) — so it was also missing everything since
then, including the entire in-browser playground and the #296 favicon fix.

## e) What we should improve (systemic)

1. **Hand-curated numbers rot.** The changelog status table had drifted on three
   axes (tests, coverage, diagnostics) because it is typed by hand. Derive it
   from `stats` (like `faq.mdx` already does) or lock it with a test
   (precedent: `hero-fixture.test.ts`, `stats.version == package.json.version`).
2. **Releases can ship releaseless-on-npm silently.** v1.2.0 sat "published" for
   ~8 hours with npm untouched because the recovery dispatch defaulted to dry-run
   and nobody watched. release.yml needs a post-publish assertion
   (`npm view <pkg> version` == tag) that fails loudly.
3. **Preregister trusted publishers before release day**, not during the
   incident. The registration is a 1-minute UI action that blocked everything.
4. **Website deploys are manual and drift for weeks** (Oct 23 → Nov 19). Either
   a deploy workflow on version tags or a scheduled staleness probe
   (compare live `/changelog/` against `package.json.version`).
5. **The release changelog page duplicates the root CHANGELOG.md** as a hand
   summary — it rots by construction (it had). Generate it or link-only.
