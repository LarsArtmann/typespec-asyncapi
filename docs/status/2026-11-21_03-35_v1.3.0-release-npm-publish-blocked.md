## d) TOTALLY FUCKED UP

The publish E404'd exactly as the 1.2.0 dispatch had. Root cause: I read "Release v1.3.0" as "attempt now, no questions", when the known external blocker was precisely the one thing worth one question. Mitigation exists (full rerun), but I burned a release run and manufactured a deadline (48h expiry) that didn't need to exist. The lesson isn't "ask more" — it's "when a release's publish path has a known owner-action blocker, confirm the blocker's status before consuming the tag".
2. **I shipped a wrong recovery instruction to three places.** TODO_LIST, AGENTS.md, and the #301 comment all said the v1.3.0 GitHub release must be created MANUALLY because "the github-release job is push-event-only and the tag's run already consumed its chance". That is false: reruns preserve the original `push` event, so a full rerun re-runs github-release automatically. I discovered the error myself during this self-review (~1 h after writing it), corrected all three (TODO_LIST edit, AGENTS.md edit blocked by the parallel session's fresher write — reconciled instead, plus a correction comment on #301). A parallel session independently reached the same correction, which confirms it — and confirms how easily the wrong version spread.
3. **I overclaimed "alerting verified working end-to-end."** What was actually verified: issue-open (on the PRE-fix workflow, with a label I created manually) and issue-close. The `-R` fix itself has never run in anger. If the label were ever deleted again and the fix were wrong, the alerting would silently die again — the exact failure mode it supposedly guards against.

The edit tool's mtime guard blocked my stale AGENTS.md write; nothing else did. There is no lock, protocol, or ownership signal for concurrent release operations on this repo.

## e) WHAT WE SHOULD IMPROVE

1. **Pre-tag publish-path check** — add to the release checklist: "confirm the registry publish path is live (trusted-publisher card state) before pushing a `v*` tag when any publish blocker is open." Cost: one question to the owner. Benefit: no dead release runs, no manufactured 48h deadlines. [TODO — release checklist row]
2. **ci-alert close condition is wrong for Release failures** — the tracking issue closes on the next green master CI run even when the failed Release run is still failed (observed live: #301 closed while the release stayed blocked). Fix: only close when no failed Release run is newer than the last green CI run. [TODO]
3. **ci-alert has no self-test** — the `-R` fix is unfalsified in production. Add a `workflow_dispatch` no-op mode (or scheduled canary) that runs the label/issue/comment/close path against a scratch issue, so the bootstrap path is exercised without a real fire. [TODO]
4. **Concurrent-session guardrail** — this session and another edited the same docs within minutes; only the editor's mtime check prevented a split brain. Cheap fix: the release checklist in TODO_LIST should carry an "owner: <session/date>" line on the active release block, and any session touching it re-reads immediately before editing (the daemon also commits underneath writers — re-read-before-edit is already the rule, this session proves why). [TODO — note in checklist]
5. **GitHub API rate-limit handling** — `gh` calls hit HTTP 403 mid-release; retried with sleeps. Improvement: batch gh queries, prefer `--json` single calls, and never poll in a tight loop during a release. [process note]
6. **CHANGELOG 1.3.0's minimatch bullet says "ESM-only advisory dismissal"** — accurate as of the tag, but stale next to the `[Unreleased]` override entry. Polish the wording at the next release so readers don't reconcile the two by hand. [TODO — next release pass]
7. **Alerting blind spot by design** — ci-alert only observes runs started after it landed, and `workflow_run` failures on forks/PRs are invisible. Acceptable, but worth stating in the workflow header so nobody trusts it as complete telemetry. [ROADMAP]
