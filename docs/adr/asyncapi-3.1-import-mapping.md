# AsyncAPI 3.1 import mapping

Companion to [ADR 0003](0003-asyncapi-importer-architecture.md). This is an inventory of what the [AsyncAPI 3.1.0 specification][spec] describes and how an importer could express it. It is not a list of implemented importer features.

**Source** means an existing TypeSpec declaration or AsyncAPI decorator can express the listed shape. **Config** means the emitter needs `tspconfig.yaml` or equivalent compiler options; a `main.tsp`-only importer cannot preserve it. **Partial** means the emitter can represent a subset or a normalized form. **Gap** means there's no faithful lowering today. These labels describe the current output surface, not the initial CLI's release scope.

## Document and shared metadata

| Spec object or field | TypeSpec or emitter mapping | Fidelity |
| --- | --- | --- |
| [AsyncAPI Object][root]: `asyncapi`, `id`, `info`, `defaultContentType`, `servers`, `channels`, `operations`, `components` | One TypeSpec service namespace for application identity; attach metadata and declarations, not a model with these fields. Parse `asyncapi` as a spec-version selector; the emitter writes `3.1.0`. Root `id` maps to the `asyncapi-id` emitter option. `defaultContentType` maps to `@defaultContentType`. Resolve the other sections as a graph. | **Source / config.** Spec version, API version, application ID, and source namespace are separate concepts. |
| [Info Object][info]: `title`, `version`, `description`, `termsOfService`, `contact`, `license`, `tags`, `externalDocs` | `@service(#{ title: … })`, `@apiVersion(…)`, and `@tags(…)`. The remaining fields map to same-named emitter options. | **Source / config.** Namespace `@doc` is not a substitute for the `description` option. Don't infer a `@versioned` history from one `info.version`. |
| [Contact Object][contact] (`name`, `url`, `email`) and [License Object][license] (`name`, `url`) | Preserve as nested `contact` and `license` emitter options, not schema models. | **Config.** |
| [Tags][tags] and [Tag Object][tag] (`name`, `description`, `externalDocs`) | Namespace, operation, and message decorations: `@tags(#[…])` with rich tag values. Resolve referenced tags when comparing or lowering. | **Partial.** The emitter derives `components.tags` by tag name and also emits those tags in `info.tags`. It cannot preserve independent component keys, tag-reference identity, or placement exactly; different definitions sharing a `name` can collapse. Server tags share the server namespace; channel tags share operation state. |
| [External Documentation Object][external-docs] (`url`, `description`) | Info uses the `externalDocs` option; rich tags accept nested `externalDocs`. | **Partial.** No general decorator for standalone documentation, a reusable documentation reference, or direct documentation on a server, channel, operation, message, trait, or schema. |
| [Specification extensions][extensions] (`x-*`, where permitted) | `@extension` on a namespace, operation, or model emits an extension on the root, operation, or **message**, respectively. Schema-specific keywords use `@jsonSchemaExtension`. | **Partial.** Preserve extensions at their original placement or report the gap; don't move extensions from `info`, servers, channels, traits, or other unsupported placements to the root. |

Evidence: [document assembly](../../src/document-builder.ts), [emitter options](../../src/infrastructure/configuration/asyncAPIEmitterOptions.ts), and [tag assembly](../../src/builders/tag-builder.ts).

## Servers, channels, operations, and replies

`Servers`, `Channels`, `Operations`, `Messages`, and `Parameters` are keyed collections, not TypeSpec object types. Keep their keys independently of display names and TypeSpec identifiers. For example, `channels.orders` can have address `orders/{region}` and a channel-local message key that differs from its referenced component key.

| Spec object or field | TypeSpec or emitter mapping | Fidelity |
| --- | --- | --- |
| [Servers / Server Object][server]: `host`, `protocol`, `protocolVersion`, `pathname`, `description`, `title`, `summary`, `variables`, `security`, `tags`, `externalDocs`, `bindings` | Namespace `@server(key, #{ url: host, protocol: … })` plus optional settings; namespace `@tags`, `@bindings`, or `@useBinding`; put security requirements in server config. | **Partial.** `url` is the configuration name for the emitted `host`; do not prepend a scheme or merge in `pathname`. The emitter normalizes and restricts protocols. Title, summary and external docs have no server mapping, and namespace-level tags and bindings apply to all servers declared on that namespace. |
| [Server Variable Object][server-variable]: `enum`, `default`, `description`, `examples` | Inline `variables` on `@server`; `values` is a supported config spelling for `enum`. | **Partial.** Resolve reusable variables before inlining and record lost reuse. The builder discovers variables only from `host` placeholders, although the spec also supports `pathname` placeholders. |
| [Channels / Channel Object][channel]: key, `address`, `messages`, `title`, `summary`, `description`, `servers`, `parameters`, `tags`, `externalDocs`, `bindings` | `@channel(address)` on participating operations. `@useChannelServer(key)` emits a root-server ref. `@doc`, `@summary`, and `@tags` on channel-decorated operations supply channel metadata. Bindings and parameters have separate mappings below. | **Partial.** The emitter uses the address as the key and creates channels via operation messages. Independent keys, unknown/null addresses, channel-only declarations, independent channel and operation metadata, title/external docs, and unused channel messages are not faithfully represented. Absent or empty `servers` means all root servers; don't invent a subset. |
| [Channel address expressions][channel-expressions] and [Parameters / Parameter Object][parameter]: `enum`, `default`, `description`, `examples`, `location` | Preserve `{name}` in the channel address. Namespace `@parameter(name, config)` registers a reusable component; the emitter attaches it automatically to matching placeholders. `location` is a runtime expression, not a TypeSpec operation argument. | **Partial.** No explicit per-channel parameter attachment or inline parameter override. Distinct definitions using the same placeholder name, or a component key different from the placeholder, cannot be mapped independently. Undecorated placeholders get synthesized descriptions. |
| [Operations / Operation Object][operation]: key, `action`, `channel`, `messages`, `title`, `summary`, `description`, `security`, `tags`, `externalDocs`, `bindings`, `traits`, `reply` | TypeSpec `op`; use `@publish` for `send`, `@subscribe` for `receive`, `@channel` for the channel, and return a named model or a union of message models. Use operation `@doc`, `@summary`, `@tags` and the security/binding/trait decorators where supported. `@operationId` can override the output key. | **Partial.** Preserve application direction, not broker or peer direction. Operation `title` and `externalDocs` lack direct mappings. Several builders look up operation decorations by declaration name rather than overridden key; when the names differ, verify metadata/ref attachment, not just the key. An absent `messages` list means all channel messages; `[]` means none and isn't represented by inventing a model or `void` message. Nonempty lists are channel-local refs and match exactly one message variant, not arbitrary reusable component refs. |
| [Operation Reply Object][reply]: `address`, `channel`, `messages`; [Operation Reply Address Object][reply-address]: `description`, `location` | `@reply(ReplyModel, "$message.header#/replyTo")` for the expressible case; `location` becomes a reply address object. The builder registers one reply message on the request channel and emits no separate reply `channel` ref. | **Partial.** Distinct reply channels, multiple reply messages, address descriptions, and reusable reply/address identity need more support. Keep the spec's constraint that an explicitly referenced reply channel has an unknown address when a dynamic reply address is supplied. |

Evidence: [server builder](../../src/builders/server-builder.ts), [channel builder](../../src/builders/channel-builder.ts), [operation discovery](../../src/builders/operation-discovery.ts), and [operation builder](../../src/builders/operation-builder.ts).

## Messages, schemas, and examples

| Spec object or field | TypeSpec or emitter mapping | Fidelity |
| --- | --- | --- |
| [Messages / Message Object][message]: `name`, `title`, `summary`, `description`, `contentType`, `payload`, `headers`, `correlationId`, `tags`, `externalDocs`, `bindings`, `examples`, `traits` | A decorated model represents a message and supplies its payload schema. `@messageId` controls the component/message key; `@message` carries `title`, `contentType`, `description` and examples. Use message decorators for attachments. | **Partial.** The emitter uses `title` for both emitted `name` and `title`, and maps `@message`'s `description` to `summary`; model `@doc` also documents the payload schema. Neither distinct names/titles nor separate description/summary/external docs are preserved. An omitted message content type inherits `defaultContentType` in the spec; the emitter otherwise inserts `application/json`, so apply the effective inherited type explicitly when needed. |
| Message `payload` and channel-local message membership | Keep message identity, payload identity, and channel aliases separate in the import graph; lower the simple case to `op …(): MessageModel` with a schema ref. | **Partial.** The emitter couples message model and payload; it may coalesce channel aliases and cannot preserve several independently decorated messages for one payload without changing the model/identity scheme. No-payload messages must not become fabricated payload schemas. |
| Message `headers` | Named application-header fields via `@header`; never import protocol headers as application fields. | **Partial.** The builder emits an object with named fields, primitive types, and optional descriptions. Requiredness, nested constraints, arbitrary schema refs, and alternate header schema formats do not round-trip through this decorator. Don't turn headers into payload properties. |
| [Correlation ID Object][correlation]: `description`, `location` | `@correlationId(location)` or namespace `@reusableCorrelationId(key, location)` plus message `@useCorrelationId(key)`. | **Partial.** The public decorators take the runtime expression but no description. Preserve header/payload selection and escaped pointer tokens verbatim. |
| [Message Example Object][message-example]: `name`, `summary`, `headers`, `payload` | `@message(#{ examples: #[…] })` carries full example records; TypeSpec `@example` is a separate convenience for typed example values. | **Source** for supported values. Prefer explicit records for headers or metadata, and keep the spec's distinction between message examples and schema examples. |
| [Schema Object][schema] (AsyncAPI's Draft-07 superset) | Reuse TypeSpec's import conversion as described in the ADR. Lower named objects to `model`, properties plus `?` for `required`, arrays to `T[]`, maps to `Record<T>`, primitives/formats to TypeSpec scalars and `@format`/`@encode`, `enum`/`const` to enums or literals, and compatible composition to unions or inheritance. Existing metadata includes `@doc`, `@summary`, `@example`, `#deprecated`, property defaults, and constraint decorators. | **Partial.** Mapping must be dialect-aware. The emitter chooses `oneOf` for all-model unions and `anyOf` for mixed variants, so syntax alone does not preserve exclusivity. `unknown` can express an unconstrained schema, but this emitter's `never` also emits `{}`; it is not the boolean `false` schema. Test closed objects, schema-valued keywords, `$ref` siblings, schema `examples`/external docs, and nullability before marking them supported. Use `@jsonSchemaExtension` only where the keyword and any embedded references stay valid on re-emission. |
| [Multi Format Schema Object][multi-format]: `schemaFormat`, `schema` | Identify the dialect from the wrapper or the specified default. Route native AsyncAPI/compatible JSON Schema through the schema adapter; keep other formats opaque until there is an appropriate converter and output representation. | **Gap** for the wrapper itself and non-native formats. The spec lists formats such as JSON Schema Draft-07, Avro, OpenAPI 3.0, RAML and Protobuf. The current `@message` `schemaFormat` setting emits a message-level field and the payload remains a generated schema ref; it does not implement the spec's `{ schemaFormat, schema }` wrapper at the payload/header/component position. |

Evidence: [message builder](../../src/builders/message-builder.ts), [schema emitter](../../src/schema-emitter.ts), [constraint mapper](../../src/constraint-mapper.ts), and [schema composition](../../src/schema-fragments.ts).

## Security, traits, and protocol bindings

| Spec object or field | TypeSpec or emitter mapping | Fidelity |
| --- | --- | --- |
| [Security Scheme Object][security]: `type`, `description`, `name`, `in`, `scheme`, `bearerFormat`, `flows`, `openIdConnectUrl`, `scopes`, as applicable | Register a reusable scheme with `@security(#{ name: componentKey, scheme: … })`. Reference it on an operation with `@operationSecurity(#{ name: componentKey })`; server security uses the server config. Preserve the scheme kind (`apiKey` and `httpApiKey`, for example, are different). | **Partial.** The operation builder emits only a component ref, so inline schemes need promotion and per-use scope differences cannot be preserved by `@operationSecurity`. Do not translate AsyncAPI requirements into OpenAPI security maps. |
| [OAuth Flows][oauth-flows] and [OAuth Flow][oauth-flow] | Preserve `implicit`, `password`, `clientCredentials`, and `authorizationCode`; within a flow preserve the applicable URLs (`authorizationUrl`, `tokenUrl`, `refreshUrl`) and `availableScopes` under the OAuth2 scheme. | **Source** for supported scheme config. `availableScopes` defines scopes offered by a flow; it is not the list requested by a particular security requirement. |
| [Operation Trait Object][operation-trait] | Namespace `@operationTrait` plus operation `@useOperationTrait`. Existing fields: `title`, `summary`, `description`, `security`, `tags`, `bindings`. | **Partial.** No trait `externalDocs`. Inline traits can be promoted if that changes only representation. |
| [Message Trait Object][message-trait] | Namespace `@messageTrait` plus model `@useMessageTrait`. Existing fields: `title`, `summary`, `description`, `contentType`, `tags`, `bindings`, `headers`, `correlationId`; `name` is derived from the component key. | **Partial.** No independent trait `name`, `examples`, or `externalDocs`. For both trait kinds preserve list order: the spec uses ordered JSON Merge Patch with target fields taking precedence. TypeSpec evaluates stacked decorators bottom-up, so test emitted order rather than copying source order. |
| [Server Bindings][server-bindings], [Channel Bindings][channel-bindings], [Operation Bindings][operation-bindings], [Message Bindings][message-bindings] | Use `@bindings` on a namespace, operation, or model for server, operation, or message placement. Use operation-level `@protocol` for supported channel mappings, or register a reusable map with `@reusableBinding` and attach with `@useChannelBinding` (channel) or `@useBinding` (other placements). | **Partial.** Preserve placement, protocol keys, `bindingVersion`, and nested values separately. `@protocol` can place fields at a different level; validation/normalization may change keys or supply versions. The reusable registry is keyed by name across the four placements, emits entries through uses, and attaches one ref per target. Diagnose same-name distinct definitions or unrepresentable versions/placements rather than moving fields. |

## References, components, and import order

- **[Reference Object][ref]:** Index keys and resolve document-local `$ref` as JSON Pointers, decoding URI fragments and pointer tokens without changing the original identifiers. Keep ref identity and use sites; don't recursively expand schema cycles. Check target type and permitted placement separately from successful resolution. Root operations link to root channels and their message entries, not straight to `components.messages`. External refs are valid in the spec but outside the first importer boundary in the ADR.
- **[Runtime expressions][runtime]:** Parameter, reply-address and correlation locations select message headers or payload at runtime. An expression can contain a pointer but is not a document `$ref`; preserve its spelling and don't pass it through the document resolver.
- **[Components Object][components]:** Keep every reusable declaration in the inventory, even if unused. The current emitter's component output isn't a generic registry:

| Component keys (all 19 spec sections) | Current lowering |
| --- | --- |
| `schemas`, `messages` | Named TypeSpec type declarations and decorated message models, subject to the message/payload and schema-dialect limits above. |
| `securitySchemes`, `parameters`, `correlationIds`, `operationTraits`, `messageTraits` | Explicit namespace definition decorators with attachment rules described above. |
| `tags` | Derived by name through `@tags`, not an independent component registry. |
| `serverBindings`, `channelBindings`, `operationBindings`, `messageBindings` | `@reusableBinding` plus placement-specific use decorators; unused definitions don't populate the output collections. |
| `servers`, `channels`, `operations`, `serverVariables`, `replies`, `replyAddresses`, `externalDocs` | **Gap** for reusable component identity. Inline or lower a *used* value only when the target supports it and diagnose the lost reuse as appropriate. Do not turn unused components into active servers, channels, or operations. |

**Suggested first slice:** Resolve local refs and trait dependencies before lowering. Start with service title/version, supported servers, static channels whose key equals the address, explicit send/receive operations, and named JSON object messages. Follow the ADR's reuse-first schema adapter and compiler/re-emitter checks. Compare effective content types, message sets, and payload validation rather than only comparing text. For every unsupported object, field, or identity relationship, report the source pointer and the fidelity loss; distinguish an explicit normalization from a missing mapping.
